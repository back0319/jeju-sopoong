# 제주 소풍 서비스 이관 절차

이 문서는 매장 대표 또는 유지보수 담당자가 새 계정에서 서비스를 재구축하는 절차입니다. 실제 연결 문자열·이메일·비밀번호는 이 문서에 넣지 않습니다. 기존 테스트 데이터의 삭제는 별도 확인 후 수행합니다.

## 1. 준비와 새 DB 생성

Node.js 22, npm, Docker(로컬 검증용), PostgreSQL 17 클라이언트를 준비합니다. GitHub 저장소를 내려받은 뒤 실행합니다.

```bash
npm ci
npx supabase login
npx supabase link --project-ref "$NEW_PROJECT_REF"
npx supabase db push
```

`NEW_PROJECT_REF`는 새 Supabase 프로젝트 ID입니다. 새 프로젝트는 서울(ap-northeast-2) 리전으로 만듭니다. CLI 명령은 `npx supabase <명령> --help`로 설치 버전의 옵션을 확인할 수 있습니다. DB 암호를 요구하면 새 프로젝트의 암호를 직접 입력합니다.

공통 재료·문항·빈 콘텐츠를 넣으려면 새 DB의 연결 문자열을 `NEW_DB_URL` 환경변수로 설정하고 실행합니다. 연결 문자열은 Supabase의 Connect 화면에서 확인하며, IPv4 환경에서는 Session pooler 주소를 사용합니다.

```bash
psql "$NEW_DB_URL" -v ON_ERROR_STOP=1 -f supabase/seed.sql
```

시드는 충돌 시 기존 값을 유지합니다. 기존 운영 데이터를 복원할 때는 **복원을 먼저 완료한 뒤** 시드를 적용합니다. 관리자 계정은 시드에 없습니다.

## 2. 데이터 백업과 복원

이전 중에는 주문 접수를 중단하고 종이 주문으로 전환합니다. `OLD_DB_URL`, `NEW_DB_URL`은 로컬 환경변수로만 설정합니다. 덤프에는 설문과 주문이 들어 있으므로 저장소에 넣지 말고 접근 권한을 제한한 별도 폴더에 보관합니다.

```bash
umask 077
pg_dump "$OLD_DB_URL" --format=custom --data-only --no-owner --no-acl \
  --table=public.ingredients --table=public.inventory --table=public.products \
  --table=public.survey_versions --table=public.contents \
  --table=public.orders --table=public.order_items --table=public.order_surveys \
  --table=public.daily_order_counters --file=jeju-data.dump
pg_restore --dbname="$NEW_DB_URL" --data-only --no-owner --no-acl \
  --single-transaction --exit-on-error jeju-data.dump
psql "$NEW_DB_URL" -v ON_ERROR_STOP=1 -f supabase/seed.sql
```

위 방식은 **마이그레이션만 적용한 빈 DB**에 복원합니다. `TRUNCATE`, `--clean`을 기존 운영 DB에 실행하지 않습니다. 테이블 간 외래 키 때문에 전체 아카이브를 한 번에 복원하고, 복원 실패 시 원인을 확인한 뒤 빈 새 DB에서 다시 시작합니다.

관리자 계정과 `order_status_events`는 이 덤프에서 제외합니다. 새 Auth 계정의 ID가 달라지기 때문입니다. 기존 감사 이력은 다음 명령으로 별도 보관합니다.

```bash
psql "$OLD_DB_URL" -c '\copy public.order_status_events TO audit-history.csv CSV HEADER'
```

관리자 ID와 과거 감사 이력까지 그대로 옮겨야 한다면 임의로 Auth 테이블을 복원하지 말고 [Supabase 공식 전체 백업·복원 절차](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)를 사용합니다. 이 서비스는 Storage 업로드를 사용하지 않으며 브랜드는 Git의 정적 파일입니다. 관리자가 등록한 외부 사진·유튜브 링크의 소유권은 따로 확인합니다.

## 3. 환경변수 교체

Vercel 프로젝트 → Settings → Environment Variables에서 아래 값을 새 Supabase 프로젝트의 값으로 바꾸고 재배포합니다. `NEXT_PUBLIC_` 변수는 빌드 시 브라우저 코드에 포함되므로 재배포가 필요합니다.

| 변수 | 값의 위치 / 용도 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase Connect 또는 Settings → API의 Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Settings → API Keys의 anon 또는 publishable 키 |
| `SUPABASE_SERVICE_ROLE_KEY` | Settings → API Keys의 service_role 또는 secret 키, 서버 전용 |
| `INTERNAL_TEST_MODE` | 내부 테스트 `true`, 확정 동의문이 있는 실제 운영 `false` |

로컬 `.env.local`도 같은 값으로 바꿉니다. `.env.development.local`이 있으면 개발 서버에서 우선 적용되므로 대상 DB를 확인합니다. 로컬 DB를 사용할 때만 이 파일을 유지합니다.

## 4. 관리자 계정 재생성

`.env.admin.local`을 직접 만들고 `ADMIN_USERNAME`, `ADMIN_PASSWORD`를 설정합니다. 아이디는 3~40자, 비밀번호는 5~200자이며 관리자 계정 관리 화면에서 변경할 수 있습니다. 이 파일은 Git에서 제외됩니다.

```bash
npm run admin:create
```

명령은 새 Supabase Auth 사용자를 생성하고 해당 ID를 `admin_users`에 등록합니다. 이미 있는 계정의 비밀번호를 덮어쓰지 않습니다. 동일 계정 재사용이 필요하면 Supabase Authentication → Users에서 ID를 확인하고 SQL Editor에서 `admin_users`에 그 ID만 등록합니다.

공용 계정의 담당자가 바뀔 때는 기존 세션을 로그아웃하고 새 자격 증명을 매장 담당자에게 비공개로 전달합니다. 공개 회원가입은 Supabase Authentication 설정에서 비활성화합니다. 고객 로그인은 없습니다.

## 5. GitHub와 Vercel 소유권 이전

1. GitHub 저장소 Settings → General → Danger Zone → Transfer ownership에서 대표의 사용자 또는 조직으로 이전합니다. 새 소유자의 수락과 접근 권한을 확인합니다.
2. 로컬 `origin`을 이전된 저장소 URL로 변경합니다.
3. Vercel 프로젝트 Settings → General의 Transfer 절차로 대표 팀에 이전합니다. 이전 대상 팀의 요금제·도메인·Git 연동 조건을 확인합니다.
4. Vercel의 Git 연결이 새 저장소를 가리키고 Production Branch가 `main`인지 확인합니다.
5. 환경변수, 서울 리전, 배포 보호 설정, 도메인이 이전 후에도 맞는지 확인하고 재배포합니다.

```bash
git remote set-url origin "$NEW_GITHUB_REPOSITORY_URL"
git remote -v
```

[GitHub 이전 안내](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository)와 [Vercel 프로젝트 이전 안내](https://vercel.com/docs/projects/transferring-projects)를 이관 시점에 확인합니다. 원격 주소만 바꿔서는 Vercel 연결이 자동으로 옮겨지지 않습니다.

## 6. 도메인과 QR

Vercel Settings → Domains에서 도메인을 추가하고 안내되는 DNS 레코드를 도메인 제공업체에 설정합니다. HTTPS가 정상화되면 고객 화면과 관리자 로그인을 테스트합니다. Supabase Auth의 Site URL도 최종 도메인으로 맞춥니다.

```bash
npm run qr -- "https://최종도메인/" public/qr.png
```

관리자 운영 화면의 공통 QR 버튼은 현재 접속한 도메인의 `/`를 가리킵니다. **인쇄 후 도메인이 바뀌면 QR을 다시 인쇄해야 합니다.**

## 7. 이관 후 점검

- 빈 DB 마이그레이션·시드 성공, 관리자 로그인 성공.
- 생산자 영상 → 원물 소개 → 동의·선택 설문 → 재료·패키지 선택 → 주문번호 발급 → 관리자 자동 반영.
- 같은 주문을 재시도해도 번호와 차감은 한 번만 발생.
- 재고 차감·품절, 취소 복구, 완료 실행 취소.
- KST 날짜와 번호, 새로고침·4시간 만료.
- 주문·설문 CSV, 구성별 CSV, JSON, 문항 코드표가 같은 기록 ID로 연결되고 기간·참여 필터가 동작.
- 로고·폰트·이미지 정상 표시, 휴대폰 QR 접속.
- 실제 운영 전 확정 동의문 등록과 `INTERNAL_TEST_MODE=false` 적용.

검증이 끝나기 전에는 기존 서비스를 해지하거나 데이터를 삭제하지 않습니다.

## 매장 테스트 반영 운영 변경 (2026-09-11)

- 재고는 `inventory.business_date` 기준이며 매일 KST 00:00에 잔여 수량만 0으로 초기화됩니다. 강제 품절 설정은 유지합니다. `juseyo-inventory-midnight` DB Cron은 UTC `0 15 * * *`이며, 실행 실패 후에는 다음 카탈로그 조회·주문·재고 변경 시 보완 초기화합니다. 영업 전에 당일 재고를 입력하세요. 전날 주문을 취소해도 오늘 재고를 늘리지 않습니다.
- Supabase Cron 화면에서 작업 활성 상태와 최근 실행 결과를 확인합니다. 임시 테스트 DB에는 Cron을 설치하지 않으며, 운영 `postgres` DB에는 마이그레이션으로 설치합니다.
- 접수 상태의 당일 주문은 관리자 전용 구성 화면에서 수정합니다. 수정 시 현재 메뉴 가격을 적용하고 토핑 수량 차이만 재고에 반영합니다. 주문번호와 설문 연결은 유지하며, 변경 전후 구성·금액·관리자를 `order_edit_events`에 남깁니다. 다른 관리자가 먼저 처리한 주문은 새로 조회한 후 다시 수정합니다.
- 주문 목록의 체크박스로 최대 30건을 묶어 메뉴와 총액을 확인합니다. 묶음은 현재 관리자 화면의 선택 상태이며 DB 주문번호를 합치지 않습니다. 묶은 모든 주문이 접수 상태일 때 일괄 완료할 수 있고, 5초 동안 일괄 되돌리기를 지원합니다. 하나라도 상태가 달라지면 전체 처리를 거절합니다.
- 취소 사유는 고객 취소·가게 취소·재료 품절·메뉴 추가·직접 입력을 지원합니다. 선택 사유와 추가 설명을 함께 저장합니다.
