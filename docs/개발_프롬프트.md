## 1. 프로젝트 개요

제주 '제주 소풍(SOPOONG JEJU)' 매장에서 쓰는 **셀프 주문 모바일 웹**입니다.
서비스명은 **'주세요'**입니다.

완성된 김밥을 파는 곳이 아니라, 고객이 재료를 고르고 **직접 김밥을 만드는
체험형 매장**입니다. 직원 설명을 최소화하고 모바일 웹이 안내를 대신합니다.

**전체 이용 흐름**

```
입장 → 공통 QR 접속 → 언어 선택 → 안내/소개 → 설문 → 원물 확인
→ 김밥 구성 선택 → 주문 완료(주문번호 발급)
→ 카운터에서 주문번호 제시 → 직원이 확인·결제 → 키트 + 토핑 수령
→ 자리에서 직접 김밥 제작 → 식사 → 퇴장
```

웹의 책임 범위는 **주문 완료(주문번호 발급)까지**입니다. 결제는 웹에서
처리하지 않고 카운터에서 오프라인으로 이루어집니다. PG 연동 없음.

**QR 정책**

- 테이블별 QR 없음. 테이블 번호 개념 없음. **공통 QR 1개**만 사용합니다.
- 일행도 각자 자기 휴대폰으로 QR을 찍고 각자 주문합니다.

## 2. 기술 스택 및 배포 환경 (확정)

개발 완료 후 **가게 대표에게 프로젝트를 이관**할 예정입니다. 따라서 운영이
단순하고, 비용이 낮고, 계정 이전이 쉬운 구성을 우선합니다.
아래 스택은 **확정 사항이며 임의로 변경하지 마세요.**

### 2-1. 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 런타임 | Node.js LTS (22.x) | |
| 프레임워크 | **Next.js (App Router)** + **TypeScript** | `strict: true` |
| 스타일 | **Tailwind CSS** | 별도 UI 라이브러리 없이 직접 구성 |
| DB | **Supabase (PostgreSQL)** | 리전 **Northeast Asia (Seoul)** |
| 관리자 인증 | **Supabase Auth** (이메일+비밀번호) | 공용 계정 1개 |
| 실시간 반영 | **Supabase Realtime** | 관리자 주문 목록 구독 |
| 배포 | **Vercel** | 리전 **icn1 (Seoul)** |
| 저장소 | **GitHub** 단일 저장소 | 고객 웹 + 관리자 한 프로젝트 |
| 패키지 매니저 | npm | 락파일 커밋 |

**추가 라이브러리는 최소한으로.** 상태관리 라이브러리, 폼 라이브러리, UI 킷,
ORM은 쓰지 마세요. 주문 진행 상태는 React 상태 + `sessionStorage`로 충분하고,
DB 접근은 Supabase 클라이언트를 직접 씁니다. 이관 후 유지보수할 사람이
없다는 전제이므로 의존성이 적을수록 좋습니다.

라이브러리를 꼭 추가해야 한다면 이유를 먼저 설명하고 확인받으세요.
(단, QR 코드 생성이나 CSV 변환처럼 명백히 필요한 소형 유틸은 예외)

### 2-2. 프로젝트 구조

```
/app
  /(customer)        고객용 플로우 (언어선택 → 주문완료)
  /admin             관리자 (운영 화면 / 데이터 화면)
  /api               서버 라우트 (주문 생성, 채번, 재고 차감 등)
/components
/lib                 supabase 클라이언트, 가격 계산, 공용 유틸
/locales             ko.json (en/ja/zh는 키만 있는 빈 파일)
/config              설문 문항 정의, 메뉴 기본값
/supabase/migrations SQL 마이그레이션
```

- **주문 생성·채번·재고 차감은 반드시 서버(Route Handler 또는 Postgres 함수)
  에서 처리**합니다. 클라이언트에서 직접 쓰기 금지.
- Supabase **RLS를 활성화**하고, 익명 클라이언트에는 읽기 권한만
  (메뉴·재고 조회 등) 부여합니다. 주문 테이블 직접 쓰기·조회 불가.
- 관리자 API는 세션 검증 후에만 동작하게 합니다.

### 2-3. 시간대 처리 (주의)

- 서비스 기준 시간대는 **Asia/Seoul**입니다.
- DB 컬럼은 `timestamptz`로 저장하되, **주문번호의 '당일' 판정과 자정
  초기화는 반드시 KST 기준**으로 계산해야 합니다. Postgres의 `now()`는
  UTC이므로 그대로 쓰면 한국 시간 오전 9시에 번호가 초기화되는 버그가
  생깁니다. `(now() AT TIME ZONE 'Asia/Seoul')::date`처럼 명시적으로
  변환해서 쓰세요.
- 관리자 화면의 "오늘의 주문"도 같은 기준을 씁니다.

### 2-4. 배포 및 환경

- GitHub 저장소 → Vercel 연동. `main` 브랜치가 프로덕션.
- 환경은 **프로덕션 1개**만 씁니다. 별도 스테이징 없이 진행합니다.
  (일정이 짧고 운영 규모가 작습니다)
- 우선 Vercel이 발급하는 `*.vercel.app` 주소로 배포해 테스트하고,
  커스텀 도메인은 나중에 연결합니다.
- 환경변수는 `.env.example`에 전부 문서화하고, 각 변수가 어디서 발급되는지
  주석으로 설명할 것.
  - `NEXT_PUBLIC_SUPABASE_URL`
  - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
  - `SUPABASE_SERVICE_ROLE_KEY` (서버 전용, 절대 클라이언트에 노출 금지)
- Supabase 스키마는 `supabase/migrations/`에 **SQL 파일로 남깁니다.**
  대시보드에서 손으로만 만들지 마세요. 이관 후 재구축이 가능해야 합니다.
- 시드 데이터(재료 4종, 추가 재료 4종, 가격, 설문 문항)를 넣는
  `seed.sql`을 함께 만들어 주세요.

**모바일 웹 UI 원칙 (가장 중요한 요구사항)**

고객 화면의 최우선 목표는 **가독성**과 **스크롤 최소화**입니다. 관광객이
매장에서 서서 또는 앉아서 처음 보고 바로 쓸 수 있어야 합니다.

- **한 화면에 한 가지 행동만.** 여러 단계를 한 페이지에 몰아넣지 말고,
  단계별로 화면을 나눠 순서대로 진행시킵니다.
- **각 단계는 스크롤 없이 한 화면에 들어오는 것을 기본 목표로 합니다.**
  선택지가 많아 불가피한 경우에만 스크롤을 허용하고, 이때도
  **주요 행동 버튼(다음/확정)은 화면 하단에 고정(sticky)** 하여 스크롤과
  무관하게 항상 보이게 합니다.
- 선택지가 화면을 넘칠 것 같으면, 문항을 나누거나 2열 그리드로 배치해
  세로 길이를 줄이는 방향으로 해결합니다.
- 버튼과 선택 영역은 손가락으로 누르기 쉽게 크게 (최소 높이 56px 이상).
  카드형 선택지, 선택 상태가 한눈에 구분되게.
- 본문 글자 크기는 16px 이상. 설명 문장은 2~3줄 이내.
- 화면 상단에 **진행률 표시**(예: 3/8 또는 진행 막대)를 고정합니다.
- 각 화면에 **뒤로 가기**를 두고, 주문 확정 전까지 언제든 수정 가능.
- 기준 뷰포트는 세로 모바일 **375~430px 폭**. iPhone SE(375×667) 같은
  작은 화면에서도 잘림이나 가로 스크롤이 없어야 합니다.
- 자동 진행(선택하자마자 다음 화면으로 넘어감)은 단일 선택 문항에서만
  사용하고, 그 외에는 명시적으로 '다음'을 누르게 합니다.

## 5. 화면 구성 (고객용)

순서대로 진행되는 단계형 플로우입니다.

### 5-1. 언어 선택
- 로고 + 언어 선택 버튼.
- 이 화면 진입 시 세션 생성.

### 5-2. 안내 / 소개
탭 또는 스크롤 섹션으로 구성. **내용은 `[미확정]`이므로 콘텐츠는 비워두고
레이아웃과 자리만 만들어 주세요.**

- 매장 이용 방법
- 브랜드 / 매장 소개
- 제주 생산자 소개

콘텐츠는 나중에 채울 수 있게 언어별 콘텐츠 파일 또는 DB 테이블로 분리하고,
지금은 "준비 중입니다" 같은 안내가 나오게 합니다.

### 5-3. 개인정보 수집 동의
- 동의 화면을 **넣되, 약관 본문은 `[미확정]`이라 비워둡니다.**
- 본문 텍스트 영역 + "동의합니다" 체크 + "다음" 버튼 구조만 만들고,
  본문은 나중에 텍스트만 교체하면 되도록 분리해 주세요.
- 동의 여부와 시각을 저장합니다.

### 5-4. 설문
- **문항은 아직 `[미확정]`입니다.** 문항을 하드코딩하지 말고,
  **설문 문항을 데이터(JSON 설정 파일 또는 DB 테이블)로 정의하고 화면이
  그걸 읽어 렌더링하는 구조**로 만들어 주세요. 문항이 바뀌어도 코드 수정 없이
  대응할 수 있어야 합니다.
- 지원해야 할 문항 타입: 단일 선택, 복수 선택, (필요 시) 단답.
- 문항별로 필수/선택 지정 가능.
- 아래 **1차 가안 8문항**을 샘플 데이터로 넣어 주세요. 테스트 이후 확정되면
  교체할 예정이므로, 데이터만 바꾸면 되는 구조를 반드시 지켜 주세요.
- **한 화면에 한 문항씩** 표시합니다. 예상 응답 시간 60~90초.

**설문 1차 가안**

| # | 문항 | 타입 | 선택지 | 필수 |
|---|---|---|---|---|
| S1 | 어디에서 오셨나요? | 단일 | 한국 / 일본 / 중국 / 대만 / 홍콩·마카오 / 동남아시아 / 미국·캐나다 / 유럽 / 기타 | 필수 |
| S2 | 연령대를 알려주세요 | 단일 | 10대 이하 / 20대 / 30대 / 40대 / 50대 / 60대 이상 | 필수 |
| S3 | 성별을 알려주세요 | 단일 | 여성 / 남성 / 응답하지 않음 | 선택 |
| S4 | 새로운 음식에 얼마나 열려 있나요? | 단일 | 익숙한 맛이 좋아요 / 적당히 열려 있어요 / 새로운 맛에 적극적이에요 | 필수 |
| S5 | 가장 끌리는 제주 원물은 무엇인가요? | 단일 | 채소 / 해산물 / 육류 / 골고루 | 필수 |
| S6 | 좋아하는 식감은 무엇인가요? | 단일 | 아삭한 것 / 부드러운 것 / 쫄깃한 것 / 골고루 | 필수 |
| S7 | 음식을 고를 때 가장 중요한 것은? | 단일 | 맛 / 건강 / 제주다움 / 이야기 | 필수 |
| S8 | 먹지 못하거나 피하고 싶은 재료가 있나요? | 복수 | 계란(EGG) / 햄(HAM) / 맛살(CRAB STICK) / PORK / TURBAN SHELL / FERNBRAKE / CARROT / 해당 없음 | 필수 |

- S4~S7은 미식 취향 문항입니다. 현재는 **추천에 사용하지 않고 데이터 수집
  목적**입니다. 추천 로직을 만들지 마세요.
- **S8은 재료 ID와 매핑되는 특수 문항**입니다. 아래 연동 규칙을 따릅니다.
- '해당 없음'을 고르면 다른 선택지는 자동 해제되게 처리해 주세요.
- 문항 정의에 `linkedIngredientId` 같은 필드를 두어, 선택지와 재료를 연결하는
  것이 코드가 아니라 데이터로 표현되게 해주세요.

**중요 — 못 먹는 음식과 재료 선택의 연동**

- "먹지 못하는 음식" 문항의 선택지는 **실제 재료 ID와 매핑**되어야 합니다.
  (예: 계란 / 햄 / 맛살 / 돼지고기 / 뿔소라 …)
- 여기서 선택한 재료는 이후 김밥 구성 화면에서 **자동으로 비선택 상태**가
  됩니다. 기본 재료는 자동으로 '빼기' 처리, 추가 재료는 선택되지 않은 상태.
- 다만 고객이 원하면 직접 다시 선택할 수는 있게 합니다. (차단이 아니라 기본값)

### 5-5. 원물 확인
- 제주 원물 4종을 카드로 소개: **제주 돼지고기(PORK), 뿔소라(TURBAN SHELL),
  고사리(FERNBRAKE), 당근(CARROT)** (반드시 이 순서)
- **일러스트는 `public/brand/ingredients/`의 파일을 그대로 사용합니다.**
  placeholder를 쓰지 마세요.
- 재료명은 **영문 표기**를 주로 사용합니다.
- 각 카드에 설명 텍스트와 영상 자리를 둡니다.
- **설명 문구와 영상은 아직 없습니다.** 빈 영역으로 두고, 관리자에서
  나중에 입력할 수 있게 합니다.
- "건너뛰기" 가능.

### 5-6. 김밥 구성 선택
주문의 핵심 화면입니다. 아래 3개 영역으로 구성합니다.

**(1) 기본 김밥 — 5,000원**
- 고정 재료(변경 불가): **김, 밥**
- 넣고 뺄 수 있는 재료: **계란, 햄, 단무지, 맛살**
  - 기본값은 모두 '포함'. 빼도 **가격은 내려가지 않습니다.**
  - 설문에서 못 먹는다고 한 재료는 자동으로 '빼기' 상태로 시작.

**(2) 특별 추가 재료 — 개당 3,000원**
- 순서 고정: **PORK → TURBAN SHELL → FERNBRAKE → CARROT**
  (제주 돼지고기 → 뿔소라 → 고사리 → 당근)
- **각 카드에 `public/brand/ingredients/`의 일러스트를 사용합니다.**
  재료명은 영문 표기가 주 표기입니다.
- 넣기/빼기 토글만 있습니다. 수량 개념 없음(재료당 최대 1개).
- 재고 0이면 선택 불가 + `SOLD OUT` 표기.

**(3) 패키지 업그레이드 — +10,000원**
- 김밥 + 라면 + 음료 + 굿즈 = 총 15,000원 세트로 변경.
- 기본 김밥 5,000원에 업그레이드 10,000원이 **추가**되는 계산입니다.
- 특별 추가 재료를 넣은 상태에서 업그레이드하면 그 값도 그대로 더해집니다.
  - 예: 김밥 5,000 + 토핑 1개 3,000 + 업그레이드 10,000 = **18,000원**
- **음료와 굿즈는 아직 준비되지 않았습니다.** 관리자에서
  **패키지 판매 ON/OFF 토글**로 노출을 끌 수 있게 하고, 초기값은 **OFF**로.
  로직과 화면은 완성해 두되 테스트 때는 노출하지 않습니다.
- 같은 방식으로 **라면 단품 추가**도 상품 구조에 넣어두되 초기에는 비활성.
  (음료·굿즈보다 라면이 먼저 준비될 수 있음)

### 5-7. 추가 주문
- 김밥 구성을 마치면 **"추가 주문하기"** 단계를 둡니다.
- 여기서 **김밥 또는 패키지를 하나 더 추가**할 수 있습니다.
  추가하면 5-6 화면으로 돌아가 새 구성을 처음부터 고릅니다.
- 즉 하나의 주문에 **여러 개의 항목(item)** 이 담기는 장바구니 구조입니다.
  항목마다 재료 구성이 각각 다를 수 있습니다.
- '인분/수량' 방식이 아니라 **항목 단위**로 관리합니다.

### 5-8. 주문 확인
- 담긴 항목 전체와 각 항목의 재료 구성, 항목별 금액, **총 금액**을 표시.
- 항목 삭제 / 수정 가능.
- "주문 확정" 버튼.

### 5-9. 주문 완료
- **주문번호를 화면 가득 크게** 표시합니다. 매장에서 이걸 보여주면 됩니다.
  이 화면에서 주문번호가 시각적으로 가장 우세해야 하며, 다른 요소가
  번호를 밀어내거나 작아 보이게 만들면 안 됩니다.
- "카운터에서 이 번호를 보여주세요" 안내.
- 총 금액을 번호 아래에 표시.

**주문 내역 보기**
- 번호 아래에 **"주문 내역 보기"** 버튼을 두고, 기본은 **접힌 상태**입니다.

  (내역을 펼쳐둔 채로 두면 주문번호가 스크롤에 묻히므로 반드시 접힘이 기본)
- 펼쳤을 때 표시할 내용: 항목별로 기본 김밥/패키지 구분, **포함한 기본 재료**,
  **제외한 기본 재료**, 추가한 특별 재료, 항목별 금액, 총 금액.

  바로 확인할 수 있게 합니다.

**새로고침 · 재접속 시 복원 (중요)**
- 주문 확정 API 응답으로 받은 **주문번호를 즉시 localStorage에 저장**합니다.
  화면 상태(React state)에만 두지 마세요. 새로고침하면 사라집니다.
- 주문 완료 화면은 항상 **localStorage의 주문번호로 서버에서 주문을 조회**해
  내역을 표시합니다. 내역 자체를 localStorage에 저장해 그대로 보여주는
  방식은 쓰지 마세요. (실제 주문과 어긋날 수 있음)
- 따라서 **주문번호로 주문 내역을 조회하는 공개 API**가 필요합니다.
  번호만 알면 조회되므로 개인정보는 포함되지 않아야 합니다.
  (설문 응답은 이 API로 노출하지 마세요)
- 고객이 브라우저를 닫았다가 다시 QR을 찍으면, 언어 선택 화면에
  **"진행 중인 주문 보기"** 버튼이 떠서 이 화면으로 바로 돌아올 수 있게 합니다.
- **저장한 주문번호의 만료 처리**: 저장 시각을 함께 기록하고,
  **4시간이 지났거나 KST 기준 날짜가 바뀌었으면 자동으로 삭제**합니다.
  그렇지 않으면 다음 날 방문한 고객에게 어제 주문번호가 뜹니다.
- 조회 결과 주문이 `CANCELLED`이면 취소되었음을 안내하고,
  저장된 주문번호를 삭제합니다.
- localStorage 접근은 **try/catch로 감쌀 것.** 시크릿 모드 등에서 막혀도
  에러 없이 화면이 정상 동작해야 합니다. (복원만 안 되면 됨)
- "새 주문 시작하기" 버튼을 두어 고객이 직접 초기화할 수 있게 합니다.

### 5-10. 체험 안내 (선택)
- 김밥 만드는 방법 영상 자리. **콘텐츠 없음, 자리만.**

## 6. 주문번호 규칙

- 당일 `001`부터 순차 증가.
- **매일 자정(KST)에 초기화**됩니다. 2-3의 시간대 처리를 반드시 따르세요.
- 동시 주문에도 번호가 중복되지 않도록 DB 레벨에서 원자적으로 채번할 것.
  (시퀀스 또는 트랜잭션 내 카운터. 애플리케이션 레벨 count+1 금지)
- 제공 순서는 번호 순이 아닙니다. 고객이 카운터에 온 순서대로 처리합니다.
  따라서 번호는 '식별'용이지 '대기순서'용이 아닙니다.

## 7. 주문 상태

카운터에서 결제와 수령이 동시에 일어나므로 상태를 단순하게 갑니다.

| 상태 | 의미 |
|---|---|
| `PENDING` (주문접수) | 고객이 주문을 확정한 상태 |
| `COMPLETED` (결제·수령 완료) | 직원이 카운터에서 결제받고 재료를 전달한 상태 |
| `CANCELLED` (취소) | 중복·오류·고객 취소 |

- 관리자에서 상태를 변경합니다.
- **취소 시 차감했던 토핑 재고를 복구**해야 합니다.

## 8. 영상

- 영상은 유튜브에 업로드하고 웹에서는 링크만 연결합니다. 영상 DB 구축 없음.
- **언어별로 다른 유튜브 링크**를 연결합니다.
  즉 `(콘텐츠, 언어) → 유튜브 URL` 구조.
- 관리자에서 콘텐츠별·언어별 유튜브 URL을 입력/수정할 수 있어야 합니다.
- URL이 비어 있으면 영상 영역을 숨기거나 "준비 중" 표시.
- 자동 재생하지 않고 고객이 눌렀을 때 재생.
- **현재 영상은 하나도 없습니다.** 전부 빈 값으로 두고 구조만 만듭니다.

## 9. 관리자 페이지

- 경로는 `/admin` 등으로 분리.
- **공용 계정 1개**로 로그인합니다. (아이디/비밀번호 방식, 환경변수 또는 DB)
- 태블릿 가로 화면과 PC 화면을 우선으로 설계. 데스크톱에서 잘 보여야 합니다.

**관리자 화면은 성격이 다른 두 관점으로 나누어 설계해 주세요.**

| 관점 | 목적 | 사용 상황 | 설계 방향 |
|---|---|---|---|
| **운영 화면** | 지금 들어온 주문을 빠르게 처리 | 영업 중, 카운터에서 서서 | 정보 밀도 높게, 클릭 최소, 키보드로 조작 가능, 새로고침 불필요 |
| **데이터 화면** | 쌓인 주문·설문을 조회·분석 | 영업 후, 앉아서 | 필터·기간 선택·표 형태·CSV 내려받기 |

두 화면을 상단 탭이나 사이드바로 명확히 분리하고, 로그인 직후에는 **운영
화면**이 먼저 나오게 합니다.

### 9-0. 운영 화면 설계 원칙

- 카운터에서 **서서, 급하게, 한 손으로** 쓰는 화면이라고 가정하세요.
- 화면을 좌우로 나눠 **왼쪽에 주문 목록, 오른쪽에 선택한 주문의 상세**를
  동시에 보여줍니다. 상세를 보려고 페이지를 이동하지 않게 합니다.
- 처리해야 할 주문(`PENDING`)이 항상 위에 오고, 완료된 주문은 아래로
  내려가거나 흐리게 처리합니다.
- 확인 팝업을 남발하지 마세요. 완료 처리는 즉시 반영하고, 대신 **몇 초간
  '실행 취소' 토스트**를 띄우는 방식으로 실수를 되돌리게 합니다.
- 재료 구성은 **포함/제외가 색과 아이콘으로 한눈에** 구분되어야 합니다.
  제외한 재료는 취소선 등으로 명확하게.
- 현재 토핑 잔여 수량을 화면 한쪽에 상시 표시합니다. (품절 임박을 미리 알게)

### 9-0-1. 키보드 단축키 (운영 화면)

직원이 마우스 없이 처리할 수 있어야 합니다. 화면 어딘가에 단축키 안내를
접었다 펼 수 있게 두고, `?` 키로도 열리게 해주세요.

| 키 | 동작 |
|---|---|
| **숫자 입력 → `Enter`** | **주문번호로 바로 이동.** 고객이 "37번이요" 하면 `37` 입력 후 Enter로 해당 주문이 즉시 상세에 뜹니다. **가장 중요한 단축키입니다.** |
| `↑` / `↓` | 주문 목록에서 위/아래 이동 |
| `Enter` | 선택한 주문을 **결제·수령 완료** 처리 |
| `Esc` | 선택 해제 / 입력 초기화 / 팝업 닫기 |
| `Ctrl+Z` | 방금 처리한 상태 변경 되돌리기 |
| `N` | 수기 주문 등록 창 열기 |
| `C` | 선택한 주문 취소 (이건 확인 절차를 둡니다) |
| `?` | 단축키 안내 열기 |

- 숫자 입력은 별도 검색창을 클릭하지 않아도 되게, **화면 어디서든 숫자를
  치면 자동으로 번호 입력 모드**가 되게 해주세요. 입력 중인 숫자를 화면에
  크게 표시하고, 일치하는 주문이 있으면 즉시 미리 보여줍니다.
- 텍스트 입력란에 포커스가 있을 때는 단축키가 작동하지 않아야 합니다.

### 9-1. 주문 관리 (최우선)
- **오늘의 주문 목록**이 첫 화면. 최신 주문이 위로.
- 목록에 표시: 주문번호, 주문시각, 항목 수, 총 금액, 상태.
- 주문을 열면 항목별 상세(포함/제외 기본 재료, 추가 재료, 금액) 표시.
- 상태 변경 버튼. 목록에서 바로 `완료` 처리할 수 있으면 더 좋습니다.
- 주문번호로 검색.
- **새 주문이 자동으로 목록에 반영**되어야 합니다.
  (Supabase Realtime 구독 또는 주기적 폴링. 직원이 새로고침하지 않아도 되게)

### 9-2. 수기 주문 등록
- 웹/인터넷 장애 시 종이로 받은 주문을 관리자가 직접 입력해 등록하는 기능.
- 고객 화면과 같은 재료 구성으로 주문을 만들고 주문번호를 발급합니다.

### 9-3. 재료 · 재고 관리
- 특별 추가 재료 4종의 **초기 수량을 영업 시작 전에 직접 입력**합니다.
- 주문이 확정될 때마다 자동 차감.
- 잔여 수량 0이면 자동 `SOLD OUT` 처리 → 고객 화면에서 선택 불가.
- 수동으로 품절/판매재개를 강제할 수 있는 토글도 함께.
- **동시 주문 대비**: 주문 확정 시점에 재고를 다시 검증하고, 부족하면 주문을
  실패시키고 고객에게 안내해야 합니다. (읽은 값 기준으로 차감하지 말 것)

### 9-4. 메뉴 관리
- 기본 김밥 가격, 추가 재료 개당 가격, 패키지 업그레이드 가격을 수정 가능하게.
- 상품(라면, 음료, 굿즈, 향후 디저트)을 **추가/활성화할 수 있는 구조**로
  만들어 두세요. 지금은 비활성 상태.
- 패키지 판매 ON/OFF 토글.

### 9-5. 콘텐츠 관리
- 원물 4종의 사진/설명, 소개 페이지 콘텐츠, 언어별 유튜브 URL 입력.

### 9-6. 데이터 화면 (조회 · 내려받기)
- 운영 화면과 분리된 별도 탭.
- 기간 선택 후 주문 목록을 표 형태로 조회. 상태·언어·재료로 필터.
- **주문과 설문 응답이 한 행에 붙어 보여야 합니다.** 나중에 "어떤 고객이
  어떤 재료를 골랐는가"를 보는 것이 목적입니다.
- **기간별 CSV 내려받기.** 파일에 생성일시와 조회기간을 표시.
- 통계 대시보드는 2차로 미룹니다. (지금은 CSV만 있으면 충분)

## 11. 개발 우선순위

**2순위**
- 설문(구조 + 임시 문항), 동의 화면, 못 먹는 음식 자동 연동

- 수기 주문 등록, CSV 내려받기, 메뉴·콘텐츠 관리

**3순위 (이번엔 하지 않음)**
- 다국어 실제 번역, 영상 연결, 통계 대시보드, 원물 추천 기능
